---
title: Разговор с лаунчером
description: Как дать доработке лаунчера половину, которая живёт на мастере.
---

Лаунчер открыт, и его меняют под себя. Почти любой доработке нужна половина на мастере —
что-то посчитать, что-то сохранить, что-то, что знает только сервер, — а мастер закрыт.
Модуль и есть эта половина.

Отдельного механизма здесь нет: это обычная ручка, которая у вас уже есть, плюс один кадр
на то направление, которое ручка закрыть не может.

## Принять то, что прислал форк

Отдельного макроса нет. Кадр от лаунчера — такое же событие, как любое другое, и
подписываются на него так же: типом аргумента.

```rust
use noro_sdk::prelude::*;

#[noro::module]
impl Module {
    #[event]
    fn on_frame(e: LauncherMessage) -> Result<()> {
        let kind = e.payload["kind"].as_str().unwrap_or("");
        log::info(format!("{} прислал {kind}", e.player.label()));
        Ok(())
    }
}
```

Форк шлёт в уже открытый сокет:

```json
{"t":"ModuleMessage","d":{"module":"ваш-id","payload":{"kind":"hello"}}}
```

Кадр доходит **только до того модуля, который в нём назван**: это половина разговора между
доработкой и её же модулем, и сосед, читающий её, удивил бы обоих. Возможность `launcher`
для приёма не нужна — кадр адресован вам, разрешать нечего.

Ответа у кадра нет. Где ответ нужен, есть ручка.

## Ответить на вопрос: ручка

```rust
#[route(GET, "/my-fork/state")]
fn state(req: HttpRequest) -> Result<Value> {
    let id = req.require_user()?;
    Ok(json!({ "points": store::user(id).get_or::<i64>("points")? }))
}
```

Форк зовёт `GET /api/modules/<ваш-id>/my-fork/state` тем же токеном игрока, которым он и
так разговаривает с мастером. Включать ничего не надо: ручка открыта любому вошедшему,
пока манифест не сказал иначе, а `req.require_user()` говорит, кто позвал.

Это путь для случая, когда форк что-то спрашивает: у ручки есть код ответа, тело и ошибка,
которую можно показать.

## Заговорить первым: кадр наружу

```rust
#[event]
fn on_paid(e: BankTransferred) -> Result<()> {
    launcher::send(e.to, json!({ "kind": "paid", "amount": e.amount }))?;
    Ok(())
}
```

`send` отвечает `false`, когда лаунчер этого игрока не подключён. Это состояние, а не
ошибка, и очереди за ним нет: кадр, который некому было услышать, пропал. Если он обязан
пережить отключение — запишите его у себя, а форк спросит при запуске.

`broadcast` уходит всем вошедшим. `is_online` и `connected` отвечают, кто на связи, и им
хватает `launcher = ["read"]`.

## Что внутри payload

Это дело пары: вашего форка и вашего модуля. Протокол несёт его непрозрачным JSON
намеренно — описанная форма сделала бы каждую правку форка релизом контракта, а смысл
делать это модулем ровно в том, что не сделала бы.

## Стоковый лаунчер всё это игнорирует

Неизвестный кадр отбрасывается там же, где разбирается: без ошибки и без обрыва
соединения. Это и есть условие, при котором доработку можно раскатить на часть машин:
игроки на стоковой сборке кадров просто не видят, и у них ничего не ломается.

:::caution[Лаунчер под AGPL]
Менять его — нормально, публиковать изменённое — тоже обязанность. Модуль, который вы
пишете против этого API, ваш и отдельный: он разговаривает через описанную границу и
ничего не линкует.
:::
